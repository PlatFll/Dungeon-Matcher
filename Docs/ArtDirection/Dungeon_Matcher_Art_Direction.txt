# Dungeon Matcher — Art Direction & Sprite Production Guide

**Version:** 1.4
**Compiled:** 2026-09-19
**Updated for production combat animations:** 2026-09-21
**Scope:** visual identity, palettes, native sprite editing, combat animation, dungeon presentation, tile VFX, sound and haptic feedback.
**Owner:** the user; new design approvals remain the user's decision.

This repository edition is the durable source of truth for the art direction established in this project conversation. It records the versions carried forward as working references, the rejected approaches, and unresolved issues. It does not retroactively approve every historical suggestion or authorize changes to shipped assets.

The PNG and ASE assets in the accompanying pack are byte-for-byte copies of supplied files. No character artwork was edited to create this documentation. Reference boards are labeled inspection layouts, not replacement sprite sheets. Versioning, status labels, and review templates are organizational conventions introduced by this guide.

## 1. Start here in every new art task

1. Read this guide and inspect `Dungeon_Matcher_Art_References.png`; use individual PNGs for exact pixels.
2. Identify the actual target file, character identity, task scope, and applicable reference status.
3. Separate what is locked from what the user has authorized you to change.
4. Choose material colors and shading based on the character's role, not a generic fantasy preset.
5. Review the output visually AND check the file's actual dimensions, palette, alpha, and placement.
6. Record the result as a candidate, working reference, or approved replacement only as warranted.

The latest explicit user decision controls. The original target controls character identity and geometry; the working reference cast controls rendering. Neither a generated lookalike nor a persuasive description overrides the actual original pixels. If sources conflict or a required target is unavailable, surface that specific gap instead of silently improvising.

This guide does not supersede gameplay, balance, story, or repository-safety instructions outside its art scope.

## 2. Theme and aesthetic

### Core fantasy

Dungeon Matcher reverses the usual dungeon story: the player is a dungeon monster/denizen defending a powerful magical artifact from outsiders. The world gradually takes that defender more seriously. Locals give way to guards, knights, royal forces, and the King, with wider adventuring factions and contextual mixtures later. This escalation should be visible in costume, equipment, discipline, and silhouette, not merely larger numbers.

### Visual promise

Cute, whimsical, nostalgic fantasy pixel art with a mysterious dungeon atmosphere and clear combat readability. Characters can be threatening or determined without becoming photorealistic, grim, over-rendered, or generic military figures. Ordinary people's improvised equipment is part of the charm: a pitchfork and a frying pan are meaningful character identities.

The current visual combination is:
- compact, readable character sprites with strong silhouettes and simple faces;
- dark purple dungeon frames and a restrained dark interface;
- bright, faceted, differentiated gems;
- readable material shading and selective magical/hero accents.

This is not painterly fantasy illustration, smooth HD pixel imitation, or a requirement to give all characters identical anatomy. A skeleton, slime, and human can have different proportions while sharing pixel density, outline treatment, shading discipline, and visual-noise level.

Earlier world-direction notes describe modest, scrappy locals/novices and coordinated, heraldic royal forces. These are identity guides, not finalized palettes for every future faction. Do not invent unapproved enemy designs to complete this document.

## 3. Rendering rules

### Pixel scale and silhouettes

Current character reference canvases are 64 × 64 pixels. Preserve the native size and occupied footprint of an existing target. A 64 × 64 image with the character shrunk inside it is not equivalent. Do not move the art to the bottom edge merely to match a comparison layout.

Preserve the established chunky contour language. Existing outlines are generally one source pixel along exposed edges, with thicker contact or corner clusters where the drawing already uses them. Do not mechanically thicken everything or force every contour into identical thickness. The actual reference art governs.

Oversized heads and compact human/skeletal bodies are common in the cast; Bardley's nonhuman body remains asymmetrical, curled, and low-spreading. Preserve distinguishing shapes instead of making every character a standard chibi doll.

### Outlines and faces

The shared CHARACTER outline/deepest separation color is `#0A0D11`. Use it for the external contour and necessary overlap/face separations, not as a new border around every interior detail. Merge accidental near-black noise in character recolors.

Preserve the original face's geometry, expression, eye shapes, and eye-light placements. Human faces may differ from monster faces. Earlier discussions explored human eye treatments; there is no universal instruction to replace every face with large black rectangles or identical white eyes. Do not add stereotyped gender cues to the Pan Villager: her existing design is the authority.

### Lighting and material clusters

Use top-left lighting for new character shading and recolor cleanup. Favor broad, connected base/shadow/light clusters. Put shadows on turning-away planes, overlaps, undersides, and recesses. Put sparse highlights on lit planes. Avoid an evenly shaded border around every object, scattered highlight noise, and smooth gradients.

Most materials need two or three visibly useful tones; a large focal material may use four. A small feature may need only one or two. Do not use every palette shade on every body part.

Material differences matter: bone is matte and broad; cloth has restrained folds; straw is warm but not metallic; iron is cool and dull with selective rim light; gold has sparse bright accents; slime is rounded through cluster shapes, not angular facets. Gem faceting is not the shading model for a skull, tunic, or slime.

### Prohibited by default in these sprite passes

No blur, gradients, dithering, painterly texture, semi-transparent edge anti-aliasing, resampling, subpixel softness, unnecessary isolated pixel noise, or automatic globally thick outlines. Keep hard native pixels. Intentional small eye glints or material accents are not forbidden simply because they occupy one pixel.

## 4. Palette philosophy and visual hierarchy

There is NOT one universal fixed palette for the entire game. Cohesion comes from compatible hue/value relationships, shared material ramps where appropriate, outline discipline, clean clusters, native pixel scale, and similar detail density.

Use the same ramp when the material is meant to relate: Farmer/Pan Villager skin and clothes; Rattlebones/Bardley gold. Allow character-specific colors: Bardley's yellow-green/plum, Rattlebones's bone/red/cyan, the Pan Villager's cool iron.

Current character references contain 14–16 opaque colors. This is a useful working range, NOT a rule that heroes must have more colors than enemies or that every future sprite must have exactly 16. The Pan Villager has 16 while Rattlebones has 15. Avoid new colors that serve no distinct material or shape purpose; authorize exceptions deliberately.

Common enemies should be modest, practical, and less extravagant—not muddy, invisible, shrunken, or carelessly shaded. Heroes can have stronger signature accents without making every surface bright. Preserve enough contrast for each face, silhouette, and gameplay-identifying prop to read.

Do not copy the gems' saturation onto an entire human outfit. Do not force heroes into brown village palettes to make them match. Design hierarchy by focal area and material, not by lowering all enemy contrast.

## 8. How to direct the next character

Start with identity, not colors. Name the actual species/person, prop, costume, personality, and visual role. Use the user's terms. A frying pan is not a shield; a musical pipe is not a wand. Identify the silhouette landmarks and facial features that must survive.

Next, compare the target to the working cast at the same pixel scale. Diagnose actual mismatches: pixel density, overly smooth shading, outline weight, near-duplicate noise, face complexity, material separation, or uncontrolled highlights. Do not call a sprite inconsistent just because it has a different hue, body shape, or necessary material.

Build the palette by material. Reuse a shared ramp where appropriate, then add only the distinct material ramp needed for that character. Choose a dominant color area, supporting materials, and small accents. Document exact hex values and shading roles before handing the task to Astra.

Decide the edit scope:
- **Review:** inspect and explain; do not edit unsolicited.
- **Recolor:** palette/material assignment; preserve geometry, pose, alpha mask, and placement.
- **Internal cleanup:** simplify clusters and improve form shading within the existing silhouette.
- **Localized redesign:** when explicitly allowed, adjust named features or silhouettes for readability while protecting character identity. Record the changes.
- **New design / major redesign:** when requested, explore new geometry separately from the original. A candidate is not a replacement until approved.

Do not demand approval for every one-pixel shading decision within an authorized cleanup. Do surface changes to identity, face design, species, equipment concept, proportions, canvas footprint, or silhouette when they exceed the requested scope. “Act as art director” is not permission to discard a recognizable original during a recolor.

### Tool/workflow preference

Follow the current task's explicit editing-tool and scope instructions. The production idle passes use LibreSprite's native pixel/cel API and LibreSprite exports. Read-only scripts inspect pixels, palettes and frame integrity; generated reinterpretations are not substitutes for these sprites. Earlier direct-script recolor preferences do not override an explicit request to use LibreSprite.

## 9. Direct recolor workflow and quality gates

### Inspect before editing

Open the actual image file. Record its native dimensions, opaque palette, alpha values, occupied bounds, and mask. Identify each material by location and meaning. Near-identical original RGB values may belong to different materials and need different replacements.

Preserve the source file and edit a copy. Do not silently overwrite the original, game assets, or animation sources. Work at native resolution; enlarge with nearest-neighbor only for inspection. A global nearest-color conversion may assist an initial pass, but it is not sufficient art direction or material assignment.

### Edit by material

Map original regions to the approved role colors. Keep the outline/facial geometry stable. Refine internal shadows/highlights deliberately. Do not infer new anatomy from shading. Preserve hand-to-prop contact and material boundaries.

For opaque character sprites, retain binary transparency when present. For a source with contaminated alpha, inspect it and document the specific allowed cleanup. Never assume a screenshot's black/checkerboard background is the actual alpha channel.

### Verify technical claims from bytes

Check actual output dimensions, allowed palette membership, number of unique opaque colors, alpha values, occupied bounds, source-mask agreement, and placement. Palette entries alone do not prove pixel colors; dimensions alone do not prove the character stayed the same size. Compare occupied masks directly when the task requires preservation.

A reference checksum helps identify the correct source version. Do not claim an exact palette count, pixel offset, preserved silhouette, or completed validation from visual impression alone. Report unperformed checks as unperformed.

### Review visually

Check at native 1×, an integer nearest-neighbor enlargement, and on both light and dark backgrounds. Compare the source, candidate, and relevant reference characters at the same native scale. A comparison board must not silently bottom-align or normalize character sizes; label any presentation transform.

Assess identity, face, silhouette, material separation, focal hierarchy, cluster simplicity, lighting, appropriate saturation, and prop readability. Mechanical validation is necessary but cannot prove artistic quality. Give a specific verdict: working reference, candidate requiring named changes, or rejected. Avoid invented numerical “style match” percentages.

Respect requested output format. When the user requests only the edited transparent PNG, deliver that file rather than a tutorial, large generated illustration, or enlarged preview presented as a 64 × 64 sprite.

## 10. Bardley exception: alpha cleanup and placement

The original Bardley source includes almost-opaque pixels plus a few faint alpha artifacts. For THAT source, the recolor brief explicitly authorized:
- original alpha ≥ 128 becomes fully opaque;
- original alpha < 128 becomes fully transparent;
- preserve the resulting solid silhouette.

This is a source-specific exception, not a global threshold rule for every sprite, effect, shadow, or UI file.

The current Bardley recolor preserves that solid shape but moves it 12 pixels downward. Original solid bounds are `(4, 11)–(57, 51)`; current recolor bounds are `(4, 23)–(57, 63)`. Its palette and rendering were carried forward, but that alignment is not settled.

Do not silently repair or canonize the offset while documenting it. Before replacement in animation/game assets, either restore the original alignment without scaling or deliberately adopt a new baseline across all relevant frames and placement settings. That historical static file remains **palette reference / placement pending**. The current production animations deliberately adopt the y=63 baseline across Bardley's idle and ability, as documented in section 11. The old static-file label remains historical provenance.

## 11. Idle-animation direction

### Established movement language

Classic planted turn-based RPG battle idle: tiny stance compression downward and controlled recovery, centered body, anchored feet/ground contact, and restrained character-specific secondary motion. It is not a jumping, floating, breathing/inflating, or wide side-to-side swaying animation.

Move the pose above the feet: slight knee/hip settling, torso/head follow-through, and a small response in held items or clothing. Do not translate the whole sprite vertically. A stable bottom bound alone does not prove both feet stayed anchored; check their actual pixel positions through the frames.

Rattlebones's skull/crown and cape express his personality. Farmer's straw hat and firmly held pitchfork express his. Do not turn secondary motion into an attack, large weapon swing, detached grip, or independently flying accessory. A slime can move differently anatomically while sharing the same restrained battle cadence; the current grounded Bardley idle is in ArtSource/CombatIdles/Bardley_Idle.aseprite.

### Production idle timing — 2026-09-20

The art-direction choice for the current cast is **130 ms for every frame**, nine frames, **1,170 ms per loop** (approximately 7.69 drawings per second). This retains Rattlebones' established waiting-for-a-turn cadence and keeps the villagers and slime in the same restrained family. The selected cadence gives the dip, blink and recovery room to read without a prolonged pause.

| Idle | Frame durations 1 through 9 (ms) | Loop |
|---|---|---|
| Rattlebones | 130, 130, 130, 130, 130, 130, 130, 130, 130 | 1,170 ms |
| Farmer | 130, 130, 130, 130, 130, 130, 130, 130, 130 | 1,170 ms |
| Pan Villager | 130, 130, 130, 130, 130, 130, 130, 130, 130 | 1,170 ms |
| Bardley | 130, 130, 130, 130, 130, 130, 130, 130, 130 | 1,170 ms |

Use this as the game's default battle-idle cadence. For future body types, review roughly 120–150 ms exposures and about 1.1–1.35 seconds per complete settle/recovery loop; those are review ranges, not automatic retiming rules. Start at nine × 130 ms and deviate only when the actual pose spacing needs it. Do not add duplicate frames solely to match a count or apply idle timing to attacks, hit reactions or VFX.

Keep feet/slime contact planted, close the blink through the low pose and reopen during recovery. Tiny scarf/cape responses trail the body by approximately one pose. Repeated ready poses can form an intentional short hold, but account for both sides of the loop seam; never add another endpoint hold during Unity export.

### Current production files and Unity placement

The current editable sources, 576×64 PNG sheets, GIFs, JSON timing and pixel-validation reports live in ArtSource/CombatIdles/. The PNG sheets remain nine 64×64 cells. The earlier cheek/scarf pass is archived. The current Farmer idle is the user's subsequently hand-adjusted LibreSprite version, preserved pixel-for-pixel and at its original nine × 130 ms timing. Pan Villager's scarf polish and Rattlebones' idle remain unchanged. Bardley's idle is translated down exactly 12 pixels, without rescaling or lost pixels, to share the ability's baseline.

Unity imports exact copies under Assets/_Game/Art/CombatIdles/, with looping UI Image clips/controllers in Assets/_Game/Animations/CombatIdles/. PlayerDefinition and EnemyDefinition remain the owners of the animation references. Idle clips contain no attack events, transform curves, root motion, scale or position keys.

Use Point filtering, no mipmaps/compression, 64 PPU and Full Rect meshes. Every frame in one character's loop has the same rectangle and bottom-center pivot. Rattlebones, Farmer and Pan Villager use fixed 64×64 rectangles.

All four current production idles now use fixed 64×64 slices. Bardley's idle and ability contact source y=63; the previous idle-only 64×52 padding crop is superseded. Idle and cast therefore retain identical source size, pixel scale and floor position. Never trim or recenter individual poses. Enemy attacks expand symmetrically to 96×64: the original 64-pixel pose moves 16 pixels right, and the bottom-center pivot moves from (32,0) to (48,0) in Unity. This preserves the same world center and floor.

The historical static reference register and hashes elsewhere in this guide describe the original reference pack, not the later animated assets. Current action and revised-idle checks are in ArtSource/CombatActions/Validation.json and AssetManifest.json. Earlier idle reports describe their archived revisions. Dungeon_Matcher_Art_References.png remains the supplied static reference board.

### Animation review convention

Inspect the loop at its actual timing, not only as a contact sheet. Check native-size readability, stable feet/contact points, body centering, grip continuity, silhouette, palette consistency, secondary-motion amplitude, and final-to-first transition. Matching frame counts alone does not establish matching style.

Do not require an identical alpha mask across animation frames: pose changes naturally alter silhouettes. Do preserve canvas dimensions and the intended world/pivot alignment. Do not force duplicate first/last poses if they create an unintended double hold; the goal is a continuous transition.

Recolor a whole animation with consistent material assignments across frames. Avoid frame-by-frame hue shifts, highlight flicker, new facial features, and asynchronous palette variants.

## 11A. Combat-action family — production defaults, 2026-09-20

The user delegated frame count, timing, attack design and ability polish to art direction for this pass. These are the current production defaults, open to later user refinement. The game is a real-time match-3 battler; the **visual acting** borrows the patient, planted charm of classic turn-based RPGs.

Keep the same recognizable head, body proportions, material ramps, dark outline and top-left lighting as the approved idles. Anticipation compresses the shoulders/body over planted feet; action travels through the torso into the held prop; recovery settles back to the exact ready pose. Faces belong to the body. Tools remain rigid, with hands visibly carrying them. Secondary cape/scarf/feather motion supports the action and follows the body. Do not add elastic handles, detached hands, floating feet, unrelated face motion, blur, subpixel interpolation or palette drift.

### Default auto-attacks

Eight drawings, **680 ms**, played once:

| Frame | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| Exposure (ms) | 80 | 80 | 120 | 40 | 120 | 80 | 80 | 80 |
| Acting | Ready | Gather | Anticipation | Fast travel | Impact | Follow-through | Recovery | Ready |

**Impact is frame 5, beginning at 320 ms.** Damage reaches the player on that rendered pose, once per accepted attack. Do not damage on frame 1 or attach the hit to an arbitrary timer unrelated to the clip. Keep the recovery within the existing enemy action ownership. The final sample emits completion at 670 ms, and the controller returns to idle at 680 ms. The runtime retains a pause-aware missing-event fallback, cancellation and duplicate guards.

Pan Villager uses a readable overhead wind-up and decisive iron-pan strike. The left edge of the pan disk is completed where the supplied source was clipped. Farmer uses a short diagonal pitchfork thrust, both hands and the entire fork moving together, with a shoulder lean and planted boots. Both use 96×64 action canvases; expand space around the body without shrinking it. Do not stack the old generic UI lunge on top of authored movement.

### Default player ability casts

Ten drawings, **880 ms**, played once on accepted activation:

### Authoring, placement and review

Start new ordinary attacks at eight drawings and casts at ten, then choose distinct useful key poses. Frame count is a production default, not a reason to insert duplicates or discard a necessary action pose. Fast travel, a readable contact/release hold and controlled recovery matter more than evenly spaced drawings. Deliberate heavy attacks may need a different anticipation, documented with their impact frame and total duration.

Sources: ArtSource/CombatActions/. Preserve supplied originals there. Edit cels and timings in LibreSprite, export untrimmed horizontal PNG sheets plus JSON durations, and verify every exported frame against its native cel. Keep clean binary alpha for these characters and only their approved colors. Fixed full rectangles, bottom-center pivots, Point filtering, no mipmaps/compression and 64 PPU apply to idle and action. Unity uses 100 Hz clip sampling to preserve millisecond exposures without an extra endpoint tick.

Review actual idle → action → idle playback at game speed and native size, then inspect each pose. Verify palette/materials, alpha, unclipped props, hand contact, stable ground, fixed center and scale across all states. In the production scene test both portrait heights, all frames, actual ability activation, hit-frame damage, duplicate events, pause longer than the fallback timeout, cancellation/restart and absent animation. Numeric palette checks do not replace visual shading review.

### Canvas and integration

Miner idle, attack and ability use **96×80**. Basket/Barricade idles use **64×64**, with **96×64** action canvases. Drawn pixels retain their original size. Fixed full-frame rectangles and bottom-center pivots preserve the same actor center and floor through every state. Never crop each pose independently or shift a pivot to follow a swinging tool. Deliberate Miner flight is an acting exception, not a centering correction.

Unity UI Images also need a stable height compensation for taller canvases: sprite pivot metadata alone does not ground a center-pivoted Image. PixelPerfectBattleCharacterUI applies this to the actor root while retaining the authoritative battle-floor anchor and normal feedback motion. Check the shared floor, clear feet above health bars, and unchanged pixel scale after portrait resizing as well as through each animation.

Native sources, horizontal sheets, GIFs, millisecond JSON, material maps and validation live in **ArtSource/LocalEnemies/**. Import with **CombatActionImporter.ImportLocalEnemies**; this extends the existing importers/controllers without rewriting the earlier four characters. BoardController remains the sole mutation owner, and EnemyAutoAttack remains the damage owner. Missing impact/completion events must have bounded, pause-aware fallback behavior. A cancelled/dead/disabled owner must not create a delayed hole or blocker.

If multiple board abilities become ready together, start each authored animation only when the board can accept its contact. Retain the ready charge while waiting; do not play an early hit pose and apply its effect after the animation has already finished.

### Combat correction lesson

Grounding checks must include connected anatomy, not just bottom-row equality.
Inspect trouser-to-boot contact through every compressed pose, candle/hat contact,
and rigid baskets/tools. Patching an entire lower row to plant feet can stretch a
held basket or detach a shin. Plant only the intended foot regions. The current
repair preserves ready poses and exposure tables, restores those connections,
uses the articulated body poses for the berry throw, and clarifies the builder's
folded knee. Miner auto-attack and the earlier four characters remain references.

### Sound and phone feedback

Keep sounds compact and readable: gem ticks/landings quietest; ordinary impacts
in the middle; player damage, explosions and the two player signatures prominent.
Use a short dry explosion, a bubbling poison puff, restrained heal/shield tones,
and distinct Bardley plucks and Rattlebones crown/bone accents. Shared enemy ability
sound provides a consistent warning. Current original synthesized sources and
measured waveform provenance live in ArtSource/Audio/.

Group simultaneous tile events, cap voices and preserve mix headroom. Never play
one explosion sound per tile. Landings may receive a very soft grouped phone tick;
hits, explosions and accepted player casts get stronger short feedback. Avoid
constant vibration on every damage tick. Music, SFX and vibration are independent
settings. Pause, focus loss and saved-run replay suppress feedback. Sound/haptics
must never own damage, targets, board resolution or animation-completion timing.

## 12. Rejected approaches and lessons that must survive

- Calling the Pan Villager a shield-bearing guard changed the brief's identity. Use the real prop and the user's character terminology.
- Generated high-resolution “pixel-style” reinterpretations changed her face, body, pose/proportions, and rendering. They are not approved references or substitutes for exact native pixel editing.
- Keeping a 64 × 64 canvas while shrinking the character fails size preservation. Check occupied bounds/masks, not just image dimensions.
- Bardley's 12-pixel translation shows that even an excellent recolor can have a production-placement issue.
- A matching palette does not guarantee matching art. Geometry, face design, pixel density, shading shapes, and detail level also matter.
- “Common enemy” does not mean “less carefully drawn” or “automatically smaller.” “Playable character” does not mean a larger arbitrary color count.
- Do not apply character outline cleanup to locked gem/UI files or make all materials shiny like gems.
- Do not preserve every early suggestion as a permanent rule: old Bardley green ramps, early idle timing, optional pan shading, and unresolved alignment must remain clearly distinguished.

## 13. Documentation and approval workflow

These are proposed organizational conventions for keeping future work consistent.

Keep one clearly marked CURRENT guide. Store prior versions in an archive, not alongside the current source with ambiguous names. Use `reference`, `candidate`, `rejected`, `superseded`, and `pending` status labels; do not describe every attractive draft as locked.

For each newly approved or carried-forward reference, record:
- character identity and gameplay/visual role;
- exact original and output filenames, hashes, native dimensions, bounds, and alignment;
- exact palette grouped by material;
- protected design landmarks and authorized changes;
- positive reference, optional refinement notes, and unresolved issues;
- approval/working-reference status, guide version, and change reason;
- animation timing and pivot/baseline implications when relevant.

Update the guide, palette data, reference board, and manifest together when the user approves a material change. Log what changed and what the new version supersedes. A minor clarification can increment a patch/minor version; a change to shared rendering or production defaults should be called out explicitly. Do not auto-publish a new global standard from one experimental sprite.

Current repository location: `Docs/ArtDirection/`. Keep native reference PNGs, palette JSON, and the guide under version control; preserve originals separately. Reference boards are for inspection, not game imports. Do not edit synced read-only Project sources or commit anything merely because this guide proposes a folder layout.

### New-chat handoff

Keep the guide and the visual reference board in the Dungeon Matcher Project sources. Keep exact individual reference files available for pixel-level editing. A message that only links to a file is not the file's contents; attach the actual guide/reference file.

Start the next task with the template in `templates/NEW_CHAT_STARTER.txt`. Use `templates/PROJECT_INSTRUCTIONS.txt` as a compact read-first rule. The full palettes and exceptions belong in the source guide, not just in a memory summary. A separate session needs the relevant files supplied or otherwise accessible; do not assume a prior sandbox path is available there.
